# Анализ текущих задач CRM и решения MVP crm-tasks

## Как устроено сейчас (CRM, Yii2)

- Базовая таблица `doc_task` (~40 колонок) + **отдельная таблица на каждый тип** `doc_task_<type>` (≈250 таблиц, связь `task_id`).
- Базовая модель `app\models\document\Task` (2600+ строк) и **≈250 PHP-классов-наследников** `Task*`, у каждого — свой контроллер/вью/форма.
- Тип задачи = запись в `enum_entity` (`class_name` указывает на PHP-класс).
- Статусы — `enum_task_status`: Новая / В работе / Выполнена.
- Результаты — общий справочник `enum_task_result` (300+ значений), а какие результаты доступны типу, **зашито в коде** класса.
- Комментарии — `doc_comment` (по `owner_id`), активность клиента — звонки `doc_call`, заказы `doc_order`, задачи.

## Что хорошо — сохранили

| В CRM | В crm-tasks |
|---|---|
| Единый набор «ядровых» полей (исполнитель, контрагент, КЛ, срок, результат, статус, приоритет) | Те же поля — колонки `tasks.task` с теми же именами, что в `doc_task` → простая миграция и те же фильтры |
| Статусы Новая / В работе / Выполнена | Те же id и названия (`tasks.task_status`) |
| Результат — цветные кнопки, выбор результата закрывает задачу | Результаты настраиваются на тип (цвет, «закрывает / оставляет в работе») |
| Таймер «Осталось 0д. 00:14:36» | Есть, плюс подсветка просрочки в списке |
| Блоки на карточке: основная информация, комментарии, активность клиента, другие задачи по контрагенту | Те же блоки — но собираются конструктором |
| Список с фильтрами, колонками, автообновлением | Есть; фильтр хранится в URL (ссылкой можно поделиться), колонки — в localStorage |
| Ссылки на справочники CRM (сотрудники, контрагенты) | Читаются напрямую из `ref_user` / `ref_contractor` той же БД |

## Что плохо — убрали

| Проблема | Решение |
|---|---|
| Новый тип задачи = новый PHP-класс, таблица, миграция, вью, деплой | Тип и форма — **данные**: конструктор + JSON-схема, без кода и деплоя |
| Результаты типа зашиты в коде | Список результатов редактируется в UI |
| ~250 таблиц `doc_task_*` | Пользовательские поля в `tasks.task.data` (jsonb + GIN-индекс) |
| Поля формы, порядок и обязательность меняются только разработчиком | Drag-and-drop, ширина поля, обязательность, «колонка в списке» |
| Нет истории изменений полей задачи в карточке | Журнал `tasks.task_event` с диффом «было → стало» по каждому полю |
| Создание из интеграций — отдельные хендлеры под каждый тип | Один формат события Kafka / REST для всех типов, идемпотентность по `event_id`, DLQ |

## Лёгкий переход (первый этап)

- Сервис работает в **той же БД**, в отдельной схеме `tasks`; таблицы CRM не меняются, только читаются.
- Блоки «Другие задачи по контрагенту» и «Активность клиента» показывают **и новые задачи, и старые `doc_task`** (со ссылкой в CRM), а также звонки и заказы клиента.
- У типа есть поле `legacy_entity_id` (id из `enum_entity`), у задачи — `legacy_task_id`: задел под перенос типов по одному и миграцию открытых задач.
- Kafka-событие может создать задачу в новом сервисе параллельно со старым механизмом — типы переводятся поштучно.

## Что сознательно не вошло в MVP

Авторизация и права, наблюдатели, перевод/делегирование задачи, вложения, SMS/e-mail из карточки, условная видимость полей, версионирование схемы с откатом, миграция исторических задач.
